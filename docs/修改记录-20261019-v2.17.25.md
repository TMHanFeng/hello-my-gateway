# 修改记录 2026-10-19 · v2.17.25 · 分组数据防误删（生产事故修复）

## 事故

2026-10-17 凌晨，生产网关的**分组收纳数据被整片抹掉**：`config.json` 的
`ui_groups` 里 16 个成员清零、`poolGroups` 整维度消失。全程接口返回 **200 OK**、
无任何提示、无日志，事后无法从界面察觉——界面上只是"分组空了"，成员自然落进
「未分组」区，看起来像"没归组"，不像"数据被删"。

**根因不是单点 bug，是四条互相独立的销毁路径**，全都以 200 静默落盘：

| # | 路径 | 机理 |
|---|---|---|
| ① | **渲染即裁剪并落盘** | `grpWrapHtml` 拿「当前页面渲染出的卡片」当全集裁剪 `members` 并 `grpSave` 落盘。而模型池页的卡片是按「普通池/专属池」模式过滤后的**子集**（`pools.html` 的 `poolMode === "user" ? isDedicated : !isDedicated`），于是**打开一次模型池页**就会把另一模式的成员当成已删除抹掉 |
| ② | **空数组上云** | `grpList` 发现本地没这个 kind 就 `d[kind] = []` 然后 `grpSave`；新设备/清过缓存的浏览器会把空数组推上服务端 |
| ③ | **拖拽按 DOM 整表重写** | `grpSyncFromDOM` 的 `byGroup[g.id] \|\| []`——不在 DOM 里的组，成员直接归零 |
| ④ | **服务端整对象覆盖** | `config["ui_groups"] = body`。前端 `grpSave` 每次 PUT 的又是**浏览器 localStorage 的全量对象**，于是客户端少带一个 key，服务端那一个维度就整个消失 |

关键事实：**分组数据只有 `config.json` 一个存储点**（数据库 20 张表里没有分组表），
所以上面任何一条触发一次，数据就永久没了，回滚数据库完全无效。

### 为什么归因容易偏

`grpSyncFromDOM` 只能清空**成员**，删不掉**组本身**；而事故证据是 `poolGroups`
整维度消失（`pgroups=[]`）——只有路径 ② ④ 能解释。把锅扣在 ③ 上会导致
"守卫只防清空"这种防不住的修法。

## 改动

### 后端（第一道防线，最可靠）

**① 按 kind 合并，不再整对象覆盖**（`app/admin/routes.py`）

```python
merged = dict(cur)                       # body 缺哪个 kind，服务端那个 kind 原样保留
for k in UG_KINDS + ("settings",):
    if k in body:
        merged[k] = body[k]
```

「缺 key」不再等于「删除」。路径 ② ④ 被这条直接堵死。

**② 收缩守卫：任何「减少」都要显式 `?force=1`**

判据是**任何减少**而不是「批量清空」——事故里路径 ① 的裁剪是 16 → 15，一次就足以
让分组数据逐步流失；若只在「清空」时才拦，这次事故根本拦不住。减少包含三种形态：

- `kind_emptied`：整个维度被清空
- `group_removed`：某个分组消失
- `members_shrunk`：某个分组的成员数变少（响应体里带丢失的成员名）

被拒时返回 400，`detail` 说明将要丢掉什么、`losses` 列出明细。

force 标志走 **query 参数**而非 body 的 key——body 是原样存进 `config.ui_groups` 的，
做成 key 会污染配置文件。

**③ 已知良好快照 + 启动自愈**（`app/core/config.py`）

每次成功保存都把分组数据另存一份 `backup/config/ui_groups.last_good.json`；
启动时若发现 `config.json` 里的分组数据**一个分组都不剩**（事故的特征签名），
自动用快照回填。用户主动"清空所有分组"是带 force 保存的，那次保存会把快照同步成
空，因此不会被"复活"。

### 前端（三面板同步：`hmg-admin/assets/hmg.js` / `index.html` / `hfadmin.html`）

| 原行为 | 现行为 |
|---|---|
| `grpSave(d)` 整份 localStorage 上云 | `grpSave(d, kinds, force)` **只提交本次改动的维度**；删除类动作才带 `force=1` |
| `grpWrapHtml` 裁剪成员表并落盘 | **渲染只读**：不裁剪、不写服务端。成员表的增删只由明确的用户动作和后端改名·删除迁移产生 |
| `grpSyncFromDOM` 按 DOM 整表重写 | **只改本次视图覆盖到的那部分**：没渲染出来的成员原样保留；DOM 里没有的组整组不动 |
| `grpList` 补空数组时顺手写服务端 | 只补内存副本，不上云 |

`grpSyncFromDOM` 的新语义是本次修复的技术核心：

```js
const rendered = new Set([...listEl.querySelectorAll(cardSel)].map(c => c.dataset[attr]));
d[kind].forEach(g => {
  if (!(g.id in byGroup)) return;                 // DOM 里没有这个组 → 整组不动
  const keep = (g.members || []).filter(m => !rendered.has(m));   // 当前视图没覆盖到的成员保留
  g.members = [...new Set([...keep, ...byGroup[g.id]])];
});
```

`rendered` 取的是**列表区全部卡片**（含"未分组"区），所以"拖到未分组区"仍然等于
"移出该组"，而"另一模式下的成员"因为不在 `rendered` 里被完整保留。

## 防复发：新增 T43 四道闸 + 修 T41 破坏性用例

| 闸 | 断言 |
|---|---|
| `T43a` | 后端按 kind 合并 + 收缩守卫在位，且 `config["ui_groups"] = body` 已消失（静态） |
| `T43b` | 只提交 `poolGroups` 时 `providerGroups` 原封不动（缺 key ≠ 删除，功能） |
| `T43c` | 成员数减少被拒（400）且不落盘；带 `?force=1` 才放行（功能） |
| `T43d` | 三面板都不再有渲染期写入与 `\|\| []` 抹组，删除类动作带 force（静态） |

**T41 用例必须同步改**：它原本把整个 `ui_groups` 整表 PUT 掉（正是事故的成因之一），
新守卫上线后会直接判它 400——红的是测试不是产品。改为**只提交 `poolGroups` 一个
维度 + 显式 `?force=1`**（它本就是"有意整表替换以拿受控夹具"），并在注释里写明缘由。

### 取证陷阱实录（首跑就被自己的注释判红）

T43a / T43d 首版都判红，但**红的是断言写法不是产品**：

- T43a 判 `'config["ui_groups"] = body' not in routes.py`，而我在 `_ui_groups_merge`
  的**文档字符串里引用了旧实现原文** → 裸子串判定命中了自己的注释。
- T43d 判 `'byGroup[g.id] || []' not in src`，而我在三面板的**说明注释里引用了旧代码**
  → 同理命中。

修法不是改注释了事，而是**把判据落到代码上**：Python 侧改用 `ast` 遍历语法树
（注释天然进不了语法树；判 `config["ui_groups"] = body` 这个 Assign 是否还存在），
前端侧先把 `//` 与 `/* */` 注释剥掉再判。

**教训**（与 v2.17.24 的 T42a 同源，但这次更隐蔽）：静态断言判"某段代码不存在"时，
**说明性注释里引用旧代码原文是常态**——裸子串判定必然误伤。判据必须落在
**可执行代码**上，否则修一次注释就要改一次断言。

## 上线须知

1. **服务端 updater 进程需重启**才能吃到新闸门逻辑：`systemctl --user restart model-gateway-updater`。
   （updater 是独立进程，代码被 pull 下来后仍跑旧逻辑，直到它自己重启。）
2. 网关进程需随更新重启（后端有改动）——updater 的 pull→重启流程会带起来。
3. 建议上线后手工核对一次：`GET /admin/ui_groups` 确认分组数据完整，
   并看一眼 `backup/config/ui_groups.last_good.json` 是否已生成。
