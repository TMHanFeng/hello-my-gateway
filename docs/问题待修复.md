## 1. ✅ 已解决 (v2.3bate) — 请求次数和 token 使用量分开统计，切换时 bug

### 问题描述
当前统计面板中，切换统计维度时，token 使用量（如 1200 tokens）会被错误地展示为调用次数（1200 次调用）。虽然此功能不常用，但属于明显的展示 bug，需要修复。

### 复现步骤
1. 打开统计面板，默认显示调用次数统计。
2. 切换到 token 使用量统计维度。
3. 观察展示数据：token 使用量（如 1200 tokens）被错误地展示为调用次数（1200 次调用）。
4. 切换回调用次数统计，数据展示正常。

### 期望行为
- 切换统计维度时，应正确展示对应维度的数据。
- 调用次数统计维度展示各时间段的 API 调用次数。
- Token 使用量统计维度展示各时间段的 token 消耗总量。
- 切换过程中数据应正确刷新，不出现数据错位。

### 影响范围
- 统计面板页面
- 用户查看统计数据时的体验
- 若用户依赖 token 使用量数据进行成本分析，会导致错误结论

## 3. ✅ 已解决 (v2.3bate) — 用户 API 密钥（api_key）未到期自动刷新

### 问题描述
用户在 dashboard 设置 API 密钥过期时间（如 5 小时或 1 天）后，到期时密钥不会自动刷新，而是保持不变。用户需要手动再次修改密钥才能重新启用，导致过期设置形同虚设。

### 复现步骤
1. 管理员为用户设置 API 密钥，并指定过期时间（例如 5 小时或 1 天后过期）。
2. 等待过期时间到达。
3. 使用已过期密钥发起 API 请求。
4. 观察到密钥状态：仍保持原密钥值不变，未自动更换为新密钥。
5. 使用过期密钥的 API 请求可能被接受（若未做过期校验）或返回固定错误（若做了校验但未刷新），用户无法继续使用服务。

### 期望行为
- **方案 A（推荐）**：到期自动刷新 —— 过期时间到达后，系统自动为用户生成新密钥并更新，旧密钥同时失效，用户无感切换。
- **方案 B（备选）**：到期后保留原密钥并做校验 —— 请求时校验密钥是否过期，过期则返回 401 并提示用户重新设置，同时日志记录该事件。

无论哪种方案，需确保：
- 过期设置生效，不形同虚设。
- 用户/管理员能知晓密钥状态（已过期 / 已刷新）。
- 过期时间、刷新时间的日志可追溯。

### 影响范围
- API 密钥管理模块（密钥存储、校验、刷新逻辑）
- 用户认证与安全（到期密钥是否仍可被使用）
- 管理后台的密钥设置界面
- 安全审计日志

## 11. ✅ 已完成 (v2.7.2) — 父池调用时子池 json_output 标记未透传

### 问题描述
当外部客户端通过 `response_format={"type":"json_object"}` 请求 JSON 格式输出时，网关在解析**父池**（如 `auto`）时会报错：

```
{"detail":"请求要求 JSON 格式输出，但该池没有任何支持格式输出（json）的模型。请在模型管理勾选"支持格式输出（json）"（默认不支持）"}
```

然而父池引用的子池中**实际存在多个 `json_output=True` 的模型**。例如 `auto` 池的引用链：

```
auto
  → SenseTime全家桶
    → DeepSeek-V4-Flash(SenseTime)   ← 含3个 json_output=True 的模型
    → GLM-5.2(SenseTime)             ← 含3个 json_output=True 的模型
    → SenseNova-6.8-Flash-Lite(SenseTime) ← 含3个 json_output=True 的模型
  → Agnes-2-Flash
  → GLM-FREE全家桶
  → Qwen全家桶
```

SenseTime 全家桶的 3 个子池共 9 个模型都开了 `json_output=True`，但父池 `auto` 调用时，网关**没有透传 json_output 标记到子池**，导致检测到"池内无支持 JSON 输出的模型"。

**临时绕过**：直接用子池名 `DeepSeek-V4-Flash(SenseTime)` 而非父池名 `auto` 即可正常调用。

### 复现步骤
```bash
# 用 auto 池 → 503 错误
curl -s -X POST "http://127.0.0.1:8650/v1/chat/completions" \
  -H "Authorization: Bearer 200202" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"返回JSON"}],"response_format":{"type":"json_object"}}'
# → {"detail":"请求要求 JSON 格式输出，但该池没有任何支持格式输出（json）的模型..."}

# 用子池名 → 正常
curl -s -X POST "http://127.0.0.1:8650/v1/chat/completions" \
  -H "Authorization: Bearer 200202" \
  -H "Content-Type: application/json" \
  -d '{"model":"DeepSeek-V4-Flash(SenseTime)","messages":[{"role":"user","content":"返回JSON"}],"response_format":{"type":"json_object"}}'
# → 正常返回 JSON
```

### 期望行为
- 父池（如 `auto`）收到 `response_format={"type":"json_object"}` 时，应**递归遍历子池**，找到 `json_output=True` 的模型并路由
- 不应仅检查顶层池内是否直接包含 `json_output=True` 的模型
- 客户端不应该需要知道子池名才能用 JSON 模式

### 影响范围
- 池路由逻辑（`pool_resolver` 或类似模块）
- 所有使用父池名 + `response_format` 的外部客户端
- Mem0 等依赖 JSON 格式输出的第三方插件

```json
Json-mini: load_balance=False
```

### 疑问点

### 需要验证
- 在一个 `load_balance: True` 且含多个模型的池中，连续发送多次请求，观察请求是否实际分配到不同模型

- 对比 `sequential` 策略与 `load_balance` 开关的交互逻辑

### 期望行为
- `load_balance: True` 时，应真正在池内多个可用模型间分配请求（轮询/随机/最少连接）
- `load_balance: False` 或 `None` 时，严格按 `sequential` 顺序使用第一个可用模型

## 22. ✅ 已解决 (v2.10.4) — Token 智能估算（系统优化）+ 智能估算超时

> **本地实现记录（2026-09-07）**：按本节既定方案在本地主线实施——①`call_metrics` 表（每模型保留 500 条样本）②估算拆两路：`est_window`（输入+max_tokens，窗口预检保持保守）与 `est_effective`（输入+历史平均输出 EMA，样本≥10 生效，决策日志/配额预检使用）③`smart_estimate=true` 且样本≥10 时非流式动态超时 `connect(10)+(输入+EMA输出)/吞吐EMA×1.3`，流式保持 120s chunk 间保底；EMA 增量更新（α=1/min(n,20)），call_metrics 历史聚合预热冷启动 ④`GET /admin/model/{id}/metrics` + 双面板编辑弹窗内联 live 区（吞吐/样本/小大请求预测耗时/预热黄条）与卡片"智能超时"徽章。远程 v2.9.13 未发布，本地先行落地。

### 设计决策（用户已确认）
1. **Token 智能估算 = 系统优化，始终生效**，与超时策略完全独立。用历史真实 actual_tokens 校准预估显示值，让 estimated_tokens 贴近真实。
2. **超时策略二选一（互斥）**：
   - 默认：用户手动填 `timeout_seconds`（未填 = 120s），**固定不变**
   - 可选：勾选「智能估算超时」→ 按 token 量动态计算超时时间（忽略手动秒数）
3. **新模型默认 `smart_estimate=false`**（固定 120s），不改变现有模型行为。
4. **前端 = 模型编辑弹窗内联 live 区**（重点做好）：勾选智能时实时显示该模型的实测吞吐、样本数、小/大请求预测超时；数据不足时黄条提示。

### 问题现状（2026-09-05 实测数据）

写入点：流式 `_settle_stream_tokens`、非流式 `execute()` 计费处（成功调用才写）。

**B. Token 估算拆两路（系统优化，恒生效）**
- `est_window`（窗口预检 `_check_available` 用）：保持现状 = 输入估算 + max_tokens（保守防超窗，不能动）
- `est_effective`（显示/预估用）：= 输入估算 + 该模型历史平均 completion_tokens（EMA 滚动），消除 max_tokens 虚高
- 决策日志/面板显示的 estimated_tokens 用 `est_effective`
- `ModelEntry` 加字段：`smart_estimate`, `throughput_ema`, `avg_completion_ema`, `sample_count`

**C. 动态超时（smart_estimate=true 时）**
```
est_total = 输入token + 该模型输出token期望(EMA)
timeout = connect(10) + est_total / throughput_EMA(tok/s) × 1.3(缓冲)
```
- 冷启动无样本 → 默认 30 tok/s（保守）
- 样本 < 10 → 回退固定 timeout_seconds（安全）
- 大请求给足时间不误杀、小请求快速判超时
- 流式每 chunk 间超时保底 120s（不误杀流式）；非流式用动态总时长

## 31. ✅ 已修复 — MiniMax 连接池"幽灵租约"堵死（PoolTimeout 每请求空耗 120s）

> **立项（2026-09-14）**：`mm` 池 MiniMax 两模型全天间歇至持续报「上游错误 → 切换 · PoolTimeout · ~120000ms · 冷却 5s」，仅兜底池 GLM 可成功；08:56 后完全堵死，重启进程前无法恢复。

### 证据链（四层账本互相矛盾，全部实测）
- **网关并发账本**（`/admin/model/{id}/load`）：`active=2, waiting=0` —— 正常；
- **httpx 连接池账本**：认为两模型各 100 连接全部在租（PoolTimeout = 等租约 120s 超时，`httpx.Timeout(120)` 的 pool 分量）；
- **操作系统 socket**：`netstat` 到 `api.minimaxi.com` 的 ESTABLISHED = **0**（进程全部出站 443 亦为 0）；
- **直连上游**：绕过网关同 key 同模型 2.7s 成功（云端已恢复）。

### 根因
1. **诱因**：08:33–08:56 MiniMax 上游劣化（真实 400 → 挂起 → 重置连接，M3 有 313 次 ReadTimeout）。
2. **泄漏本体**：httpx 流式响应被弃置时不会自动归还连接租约。网关流式链（`StreamingResponse → generate() → _wrap_key_stream → openai_sse_to_anthropic → pool._wrap_stream → provider.chat_stream`）原仅 `pool._wrap_stream` 最外层一处 finally，链上任一环在取消/断开时断裂（如二次取消打断 finally），下层 httpx response 永不关闭，httpcore 把租约永久记为在租——"幽灵租约"。
3. **慢性积压**：00:02 即有 PoolTimeout（早于当日上游劣化），03:22–03:35、08:16–08:54 的成功窗口说明 GC 偶尔回收弃置生成器可部分归还；08:56 起积压过临界点（100/100），之后零成功、零 ReadTimeout（连真实连接都拿不到），且**无任何自愈路径**。

### 修复（v2.12.3）
1. **aclose 链确定性关闭**：`main.generate()`、`_wrap_key_stream.gen()`、`format_adapter.openai_sse_to_anthropic` 三处补 `finally: await 下游.aclose()`，客户端任意时刻断开/取消，租约逐层即时归还，不再依赖 GC。
2. **自愈熔断**：`ModelEntry.pool_timeout_streak` 计数，`ModelPool._note_pool_timeout` 连续 3 次 PoolTimeout → aclose 旧 client 并经 `_build_provider`（自 `_get_provider` 提取的共用工厂）重建，堵死态数秒内恢复，无需重启；`_get_provider` 协议分支提取共用。
3. **明确不做**：`httpx.Timeout` pool 分量（默认与读超时同 120s）保持不变，交由部署者按需自行调整。

### 状态
✅ 已完成（v2.12.3，2026-09-14；回归新增 T16：连续 3 次 PoolTimeout 触发重建/计数清零/新 client 就位，79→87 断言全绿）。

### 现象
1. **请求侧**：客户端传入的某些请求参数可能在网关被过滤/改写，未按"透传请求字段"送到上游；期望行为是"未设置依赖中转站默认，设置则原样透传，两头都不能丢"。

- mem0 记录：`v4.1(deepseek-flash)` 与 `k3(kimi-k3)` **上游恒返回 cached_tokens=0**，记账正常但**无折扣收入**。

3. `reasoning_effort` 等中转站自有参数：未设置 vs 设置的优先级是否真按"透传/中转站优先"。

### 审计结论（2026-09-28，本地主线 6bcbe5f 全链路核查）

**A. 请求侧——确有网关剥离，根因实锤**
- 入口 `main.py:176` `ChatCompletionRequest(**body)`：模型为封闭 Pydantic（无 `extra="allow"`），**白名单外字段解析即静默丢弃**——`seed`/`user`/`n`/`top_k`/`logit_bias`/`logprobs`/`parallel_tool_calls`/客户端自带 `stream_options`/`metadata`/`enable_thinking` 等常见参数全部到不了上游。唯一透传通道是网关私有 `extra_params`（普通客户端不会用）。**违反"用户发什么中转发什么"**。

- 网关读取链无问题：v2.14.2 已实测 DeepSeek 真实命中可记账（2 次调用 508 命中/776 未命中/75 输出）；v4.1/k3 恒 0 是**上游不随响应回报缓存统计**（模型侧无缓存或该端点不返回）。网关唯一的"剥离"发生在非流式响应回传层（展示层），不影响记账/统计。

## 40. ✅ 已修复 — 调用记录疑似"时间倒挂"（前端列表排序致不同时刻记录混排）

### 现象
用调用记录列表时，部分 **18:53 的记录（Zcode / Limited-Model 池 / 「OpenCode Zen/Space Bunny Free」，实际约 21.9 万 token）排在了 21:57–21:58 的记录（AFlow / DeepSeek-V4.1-Flash 池）之前**，疑似时间倒挂（更早发生的记录被排到更晚记录前面）。

### 排查结论（2026-09-26，gateway.db 只读实证）
- 查询 `gateway.db` 调用记录原始 `ts` 字段：AFlow 那批记录 ts **单调递增**（21:57:12 → 21:57:15 → 21:57:20 → … → 21:58:08）；服务器当前时间（22:28）晚于全部记录，**无未来时间戳**。
- `call_metric` 同样递增（21:58:04 → 21:58:07 → 21:58:08）。
- **结论：存储层（数据库）时间戳无错乱、无倒挂。** 用户看到的"倒挂"应是**前端列表视图排序规则**把不同时刻的记录凑到了一起（按 caller、按估算 token 量等维度，而非严格按时间倒序），而非真实时间错乱。

### 根因定位与修复（2026-09-28）
- **库层复核**：本地库 1294 行（09-16~09-28）`ORDER BY id` 扫描 ts 倒退>60s **零异常**；且全库唯一写入口 `db.log_decision` 的 ts=写入时刻（`time.time()`）、id 自增，两者恒同调——库层不可能产生 id/ts 错位。
- **真根因（前端）**：两面板 `loadDecisions`（hfadmin/index 同逻辑）的增量刷新把"新进入 DOM 的卡片"**整块盲插到列表最顶部**，该假设只在"新卡片必比 DOM 既有卡片新"时成立。用户切换池筛选（或任何使旧记录首次进入列表的操作）后，先前被滤掉的**旧记录**作为"新卡片"也被盲插到顶部，压到本就更晚的记录之上——正是 18:53 Limited-Model 排到 21:57 AFlow 之前的机制。非按 caller/token 分组，纯插入位置错误。
- **修复（最小改动）**：双面板 `loadDecisions` 新卡片改为**按决策 id 定位插入**——插到第一张 id 更小的卡片前（没有则追加末尾），列表恒按记录时间倒序；其余增量逻辑（按 id 复用卡片就地更新、掉出窗口移除、新卡片入场动画）不变。

## 46. ✅ 已修复（v2.16.4，2026-10-09） — one_time 模型：额度上限被调高后 `expired` 标记不自动解除

### 现象（2026-10-03 实测确认）
`VX-CodingCompetition` 面板显示**「已失效」**，但用量明明还有剩余：

| 项 | 值 |
|---|---|
| `one_time_state.used_tokens` | 2,004,921 |
| 生效总额度（`max_tokens`） | 20,000,000（**后被用户调高**） |
| 剩余 | 约 90% |
| `one_time_state.expired` | **1（失效）** |

即：**额度消耗完毕后模型被判失效；用户随后在面板上调高总额度，系统并未据此重新判定，`expired` 标记仍停留在 1，模型无法继续使用。**

### 根因
`expired` 是**一次性写入的粘滞标记**，只在「判定额度耗尽」的那一刻被置 1；而「总额度被用户调高」这条路径**没有触发重新判定/复位**。二者缺少联动，导致：

```
额度耗尽 → expired=1
用户调高总额度 → 配置已更新，但 expired 仍为 1 → 面板显示失效、调度跳过
```

### 影响
- 用户侧：面板显示"已失效"且无法自行恢复，只能改数据库或改回原额度
- 调度侧：即使额度充足，`expired=1` 的模型仍被排除在候选之外

### 临时绕过（已验证有效）
停服 → `UPDATE one_time_state SET expired=0 WHERE model_name='<模型id>'` → 起服。
执行后实测：`DeepSeek-V4-Flash` 池与 `auto` 池均 0.7s 返回正常。

```bash
systemctl --user stop model-gateway.service
sqlite3 data/gateway.db "UPDATE one_time_state SET expired=0 WHERE model_name='VX-CodingCompetition';"
systemctl --user start model-gateway.service
```

⚠️ 仅治标——只要不再触发同样的置位条件，标记不会自己变回 1，但只要额度再次耗尽又会复现。

### 修复方向（待实施）
1. **配置变更联动**：模型额度相关字段（总额度 / 日限额 / `gift_grant_cap` / `valve_pct`）经 `PUT /admin/models` 修改后，若新上限 > `used_tokens`，则**自动清除 `expired`** 并记一条复位日志（含复位前后数值）。
2. **判定幂等化**：`expired` 不应是单向粘滞位，而应由「当前用量 vs 当前上限」**每次推导**得出；若必须持久化，则在每次配置热加载时统一重算一次。
3. **面板可见性**：模型被判定失效时，应在 UI 上提示「可通过调高额度恢复」，避免用户只能改库。

### 关联配置隐患（同源，建议一并厘清）
- **`max_tokens` 语义混淆**：该字段本意是"单次请求最大输出 token"，但当前被当作 **one_time 模型的总额度上限**参与耗尽判定（曾出现 `max_tokens=1,200,000,000` 与 `context_window=200,000` 自相矛盾的配置）。

- **`valve_pct` 乘零边界**：若公式写成 `used >= cap * valve_pct / 100`，当 `valve_pct=0` 时恒真 → 瞬间判死；应 clamp 到 `[1,100]`。

## 51. ✅ 已修复（v2.16.4，2026-10-09，轻方案） — 管理员（服务器密钥）调用的 token 用量不计入用量历史

### 现象
使用**服务器管理密钥**（`server_admin`，即配置里的服务器密钥）调用网关时，面板「用量历史 / 用量统计」里**查不到这些调用的 token 消耗**；而普通 API Key（`key_user`）调用的用量正常显示。

### 根因（2026-10-03 代码 + DB 实证）
`app/main.py` 的 `authenticate()` 对服务器密钥统一返回 **`key: None`**：

```python
# app/main.py:80-83
if not expected:
    return {"kind": "server_admin", "key": None}
if token and token == expected:
    return {"kind": "server_admin", "key": None}
```

而用量入账 / 限额判定链路全部以 `key` 对象为前提：

```python
# app/main.py:503 / 558 等
key = auth.get("key")
is_user_key = auth["kind"] == "key_user"
caller = "管理员" if auth["kind"] == "server_admin" else (key.get("name","") if key else "")
caller_key_id = (key.get("id") if key else None) or None
```

`key` 为 `None` ⇒ 没有 key_id ⇒ 各处 `if key:` 的**按 key 聚合/配额写入分支被整体跳过**，自然不会出现在按 key 维度的用量统计里。

### DB 实证（数据确实"有"但不在这张表）
- `decision_log`：**管理员 374 次 / 4,112,150 tokens** —— 调用与 token 都记了
- `api_key_usage`：仅 2 行（key_id=1、2），服务器密钥无对应行 —— **用量历史的数据源按 key_id 聚合，故查不到**
- `api_keys` 表中也没有"服务器密钥"这一条记录

即：**问题不是"没记账"，而是管理员调用没有 key 身份，无法被按 key 维度的用量统计聚合到。**

### 影响
- 面板「用量历史」看不到管理员（服务器密钥）流量
- 管理员调用无法纳入任何按 key 的预算/限额统计（当前设计本就不限管理员额度，故无功能故障，但**可观测性缺失**）

### 修复方向（待实施）
1. **为服务器密钥建立可识别身份**：在 `authenticate()` 中为 `server_admin` 分配一个稳定的虚拟 key 标识（如 `key_id = 0` 或新建一条 `type='server'` 的 api_keys 记录），使入账链路能识别。
2. **按 key 聚合时纳入虚拟身份**：`api_key_usage` / 用量历史接口对 `caller='管理员'` 的记录单独归集（可用 caller 维度而非 key_id 维度）。
3. **面板补一行"管理员（服务器密钥）"**：与其余 API Key 并列展示 token 用量与调用次数。
4. **审计留痕**：服务器密钥流量在 `decision_log` 已有记录，建议在面板上直接暴露该口径，避免"看不到=没发生"的误判。

2. 打开面板「用量历史」→ 应出现"管理员"条目的调用次数与 token 合计
3. 与 `decision_log` 中 `caller='管理员'` 的同期记录对账，数值应一致

## 52. ✅ 已修复（v2.16.4，2026-10-09） — 用量历史曲线越界（低于 0 / 高于实际最大值）【根因修正：非 Bezier，是单调插值漏限幅】

### 现象
「用量历史」图表中，为了美观对折线做了**平滑（bezier）拟合**，结果是曲线在数据点之间插值出**超出实际取值范围**的位置：
- 曲线**低于 0**（token 用量不可能为负）
- 曲线**高于该时段实际最大使用值**

即：平滑曲线不再经过数据点约束，出现"视觉上比真实数据更高/更低"的失真。

### 根因（2026-10-03 代码实证）
面板前端绘制折线时使用 **Bezier 平滑**（`static/hfadmin.html` 实测存在 `bezier` 曲线控制代码）。标准三次/二次 Bezier 仅以端点为控制点，**不保证曲线位于端点包围盒内**，数据点剧烈波动时（低值紧邻高值）会在两点之间"甩出"数据范围。

### 影响
- 图表**纵轴刻度被拉偏**（因为出现负值，坐标轴被迫扩到负数区间）
- 用户可能误读为"用量为负"或"峰值远超实际"
- 与 #49 的拖拽排序无关，属独立的可视化正确性问题

### 修复方向（待实施）
1. **改用单调插值**：把平滑实现替换为 **monotone cubic / monotone spline**（保形插值，保证每个区间内不超出相邻数据点范围），从根本上杜绝过冲。
2. **兜底钳制**：绘制后对每个采样点做 `y = clamp(y, 0, max(数据值))`，并在坐标轴计算时**忽略负值**（token 用量下界恒为 0）。
3. **可关闭平滑**：提供"平滑/折线"开关（默认折线，可选单调平滑），对准确性敏感的场景由用户自选。
4. **同步修正坐标域**：Y 轴下界固定为 0，不因插值产生的负值而扩展。

### 验证方法（修复后）
1. 造一段剧烈波动数据（如 0 → 10000 → 0 → 8000 → 0）并出图
2. 确认曲线上**不存在负值**，也不存在超过该时段最大值的点
3. Y 轴下界为 0

### 状态
✅ 已修复（v2.16.4，2026-10-09）。**根因修正**：双面板曲线已是 Fritsch–Carlson 单调三次插值（本条原文"使用 Bezier 平滑"不成立——bezier 命中均为 CSS 过渡曲线），真凶是**漏了限幅步骤**（|tg|≤3·min(相邻斜率)）：数值实验证明文档给的纯尖刺序列（0→10000→0→8000→0）反而不越界（乘积≤0 置零规则罩住），而真实流量的爬坡/平台/回落形态（相邻段斜率同号但差异大）会越界——24h 混合形态曲线低至 -259、高出峰值 131。修复=补一行限幅（双面板 loadKeyUsage），无需换算法；Y 轴下界 0 随限幅自然成立。回归外验证：文档尖刺序列+爬坡/回落序列双注入数值采样确认不再越界。
