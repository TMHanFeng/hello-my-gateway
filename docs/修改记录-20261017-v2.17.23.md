# 修改记录 2026-10-17 · v2.17.23 · 模型池改名导致分组成员丢失

## 反馈

> 「模型池分组数据更新后丢失了，检查代码」

## 根因

**分组成员存的是「池名字符串」，不是对象引用**，而 `rename_pool` 只迁移了池字典本身和
其他池里的 `pool:old` 子池引用，**完全没动 `config.ui_groups.poolGroups[].members`**。

`routes.py` 改前的 `rename_pool` 只做两件事：

```python
pools[new_name] = pools.pop(pool_name)          # ① 池字典改名
old_ref = f"pool:{pool_name}"; new_ref = ...   # ② 其他池里的 pool:old 引用
for pname, pcfg in pools.items():
    if old_ref in ids: pcfg["model_ids"] = [...]
```

后果链条：

1. 池改名后，`grpWrapHtml` 按 `items.filter(i => (g.members||[]).includes(i.id))` 过滤渲染，
   `i.id` 已是新名、成员表里还是旧名 → **匹配不上，成员静默从分组消失**，掉进「未分组」。
2. 更糟的是**放大效应**：下一次任意拖拽触发 `grpSyncFromDOM` 时，它按 DOM 重写整张成员表
   （`g.members = byGroup[g.id]`），把旧名**彻底抹掉**——用户此后无从察觉、也无从恢复。

## 实测复现（8660，修复前）

```
重命名前 分组: Model模型:DeepSeek-V4-Flash|Qwen全家桶
POST /admin/pools/DeepSeek-V4-Flash/rename {"new_name":"DS-V4-Flash"}  → 200 {"ok":true}
重命名后 分组: Model模型:Qwen全家桶                    ← 成员丢了
页面渲染   : DS-V4-Flash 掉进了 __ungroup__
```

接口返回成功、前端无任何报错——所以这属于**静默数据丢失**，用户只能靠肉眼发现。

## 修法

新增共用迁移函数 `_ui_groups_migrate_member(config, kind, old, new=None)`（`new=None`
表示成员已删除、直接剔除）。普查后发现**共有 5 处**改池/删实体的路径都漏了这条维护：

| 处理器 | 漏改后果 | 本轮 |
|---|---|---|
| `rename_pool` | **成员静默从分组消失 + 下次拖拽抹除旧名** | 改名迁移 |
| `delete_pool` | 悬空引用，分组计数徽章偏大 | 剔除成员 |
| `delete_provider` | 同上（成员存供应商 id） | 剔除成员 |
| `delete_api_key` 级联删专属池 | 同上（每个专属池都留一条死名） | 逐个剔除 |
| 删密钥的专属池 | 同上 | 剔除成员 |

后两处是普查 `del pools[...]` 时顺带发现的：删一个密钥会级联删掉它的专属池，
每个都会在成员表里留一条死名——属于同类问题的隐藏实例。

## 顺带厘清：供应商改名为何不受此影响

`providerGroups.members` 存的是供应商 **id**，而模型页的编辑弹窗把 id 设为不可改
（`routes.py` 里 `if key == "id": continue`），改名走的是「新建 + 删除」——**id 不变**，
所以不存在池改名那种「名字对不上」的失配路径。供应商只有**删除**会留悬空引用，已一并修。

## 验证（8660）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 池改名 `DeepSeek-V4-Flash`→`DS-V4-Flash` | `Model模型:Qwen全家桶`（丢失） | `Model模型:DS-V4-Flash\|Qwen全家桶` ✅ |
| 池渲染归属 | 掉进 `__ungrouped__` | 留在 `gmodel` 内 ✅ |
| 删池 `zz-del-test` | 成员表留死名 | `["zz-del-test","Hermes"]` → `["Hermes"]` ✅ |
| 删供应商 `dotsai` | 成员表留死 id | `["dotsai","intern-ai"]` → `["intern-ai"]` ✅ |

`routes.py` 语法检查通过；回归 293/293 全绿。

## 防复发：新增 T41 三道闸（防止以后再犯）

修复本身只是止血——真正的问题是**这类漏改没有任何测试能拦住**，所以同一轮补了回归断言，
让以后任何人再漏改同一类路径时套件直接红：

| 闸 | 类型 | 断言 |
|---|---|---|
| `T41a` | 静态 | `_ui_groups_migrate_member` 存在且**恰好 5 处调用**（改名迁移 / 删池 / 删供应商 / 密钥级联删专属池 / 删专属池），少一处即红 |
| `T41b` | 功能 | 建池 → 入组 → 改名 → 成员表必须跟着改名（`zzgrp2` 在、`zzgrp` 不在），**直击本轮病灶** |
| `T41c` | 功能 | 删池后成员表剔除悬空名，且**不能误删同组其他成员**（`zzsw` 须保留）——防「修过头」 |

T41b 是对病灶的**行为级**断言：修复前该场景实测成员表为 `['zzsw']`（`zzgrp2` 缺失），
断言必然失败；修复后为 `['zzgrp2','zzsw']` 通过。已在本轮 8660 上前后各验过一次。

套件卫生：`deep_clean()` 登记了 `zzgrp` 测试池的清理，并把 `config.ui_groups` 整节按
用例前快照 `UG0` 原样还原（比照既有 `QM0` / `CK0` 的做法），用例中途崩溃也不污染生产配置。

回归 **293 → 296** 全绿。

## 测试方法论坑（本轮实录，与本修复无关）

跑回归时出现 T29h 崩溃（`row["selected"]`，`row` 为 None），一度以为是自己改坏了后端。
实为**测试环境干扰**：

- 回归套件自起的网关（**8678**）与常驻实测实例（**8660**）**共用同一个 `data/gateway.db`**；
- 我在套件运行途中重启了 8660，其启动时的 `init_db()` 与调度器会和套件正在造的数据
  （`zzbt/*` 测试模型、配额行）互相踩，T29 之后的断言随级联失败。

**纪律**：跑 `tests/test_billing_regression.py` 之前必须先停掉 8660（以及任何指向同一
`data/gateway.db` 的网关进程），跑完再起。套件的 8678 与实测的 8660 不可并存。
